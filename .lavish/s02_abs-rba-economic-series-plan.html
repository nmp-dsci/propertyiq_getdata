02What the investigation found

I did not read the "Data downloads" xlsx page you linked and reverse-engineer it. The same numbers sit behind the ABS Data API — SDMX 2.1 REST at https://data.api.abs.gov.au/rest/ — which returns CSV directly. That is a far better ETL surface than scraping spreadsheet links.

The "Total Value of Dwellings" release = two SDMX dataflows, both live to 2026-Q2

  • RES_DWELL_ST — value of dwelling stock, number of dwellings, mean price, for all 8 states/territories + Australia. Exactly the tables on the page you linked.
  • RES_DWELL — median price and transfer counts for established houses and attached dwellings, by GCCSA — every capital city and rest-of-state (26 regions). This is the closest thing the ABS still publishes to a house price index.
  • RPPI (Residential Property Price Index) is discontinued — last observation 2021-Q4. Do not build on it; TVD replaced it.

How the API behaves (verified)

One URL shape for everything

GET /rest/data/ABS,{DATAFLOW}/{KEY}      # no startPeriod → full history
Accept: application/vnd.sdmx.data+csv;labels=both

{KEY} is dot-separated dimension codes in DSD order (the count must match the DSD exactly — one dot short returns 404); + ORs values, empty = all. labels=both gives 1: New South Wales in every dimension column — no separate codelist join needed.

Structure is discoverable

/rest/dataflow/ABS?detail=allstubs lists 1,227 dataflows. /rest/dataflow/ABS/{ID}?references=all gives the dimension order and every codelist. The new module should cache these, not hardcode labels.

Anomaly: every dataflow carries the annotation NonProductionDataflow=true, including CPI and LF. It is meaningless for us — ignore it.

Failure signature

A key that matches nothing returns HTTP 404 with body NoRecordsFound, not an empty CSV. Same for a period after the last release. The pull stage must treat 404+that body as "zero rows" (and raise, per repo convention), not as a transport error to retry.

No auth, no documented rate limit; keep one request per dataset per run and a real User-Agent.

Interest rates are not ABS — they are RBA

F1.1 — money market, monthly

rba.gov.au/statistics/tables/csv/f1.1-data.csv. Cash Rate Target monthly average, interbank overnight rate, BABs, OIS. Series IDs in row 10 (FIRMMCRTM etc.).

F5 — indicator lending rates, monthly

f5-data.csv. Housing loans: banks variable standard/discounted, 3-year fixed, owner-occupier vs investor; securitised outstanding averages. The mortgage-rate series a property model actually wants.

A2 — policy changes, as announced

a2-data.csv. Every cash rate target change since 1990 with its date — the event series. (F1 daily also exists but is overkill; monthly F1.1 is enough.)

RBA CSVs share one layout: a title line, then Title / Description / Frequency / Type / Units / (blank) / Source / Publication date / Series ID header rows, then DD-MMM-YYYY,val,val…. Parse by locating the Series ID row and using those IDs as the stable column keys (titles get re-worded; IDs don't). Requires a browser-like User-Agent (default curl UA is blocked). Two date formats: F1.1/F5 use DD/MM/YYYY, A2 uses DD-MMM-YYYY — parse both explicitly, never dayfirst guessing. The files are padded with thousands of blank lines at the end; drop them. Pre-1990 rows in A2 contain ranges like 17.00 to 17.50 — keep as text in raw, coerce to NaN in normalized.

04Proposed design

Follows the repo rule: one cohesive module per source under sources/, source-agnostic mechanics in core/, one publish target per module under sinks/. Two stages (pull, transform) — no extract, because the API already returns tidy rows.

Each run pulls every registered dataset in full (they are small — hundreds to a few thousand rows), then keeps the snapshot only if its content differs from the last one in the manifest.

Rule: every pull takes the full history the publisher offers

  • ABS: no region filter and no startPeriod parameter, ever. The API returns the whole series from its first observation (CPI 1948-Q3, ERP 1981-Q3, LF 1978-02). The largest full pull is LF at 37,248 rows / ~6 MB; the whole registry is ~60k rows / ~12 MB per snapshot — small. SeriesSpec therefore has no start_period field, so nobody can accidentally truncate a series.
  • Where the ABS split a series across dataflows (building approvals ×3), the registry lists all of them under one dataset and transform concatenates by period_start, keeping dim_DATAFLOW so the seam is visible.
  • RBA: the CSVs are always complete (F5 back to 1959, F1.1 to 1969, A2 to 1990); nothing to configure.
  • Discontinued but long series (RPPI 2002–2021) are pulled once as frozen datasets so the historical depth is not lost.
  • Test: test_registry_has_no_start_period plus a live smoke assertion that each dataset's earliest period_start ≤ the value pinned in the catalogue above.

Why snapshot-per-release, not period partitions

The problem: ABS revises history

Seasonally-adjusted series re-estimate every release; TVD rows come out flagged p (preliminary) and later flip to r (revised) with new values; CPI was rebased to Sep-2025=100 in v2.0.0 so every historical index number changed. A period=2024-Q1.csv partition written once and never touched would silently go stale — the opposite of what "idempotent" is supposed to mean here.

The fix: the partition key is the vintage

normalized/abs_ts/cpi/asof=2026-09-21.csv holds the full series as the ABS published it that day. Transform computes the file's sha256, compares to the newest manifest row for that dataset, and does not write if identical — so a weekly cron produces a new file only when the ABS actually released something (≈12/yr for monthly series, 4/yr for quarterly). Whoever consumes the data takes max(asof) per series — the same rule downstream already applies to rentboard's rewritten trailing month.

Cost: ~10 kB–1 MB per snapshot; a few MB per year per dataset. Cheap enough that the simplicity wins. Alternative B (rewrite trailing N years by period) is in D1 if you disagree.

08Risks & failure modes

Dataflow version bumps rebase indexes

CPI went 1.x → 2.0.0 with a new base (Sep-2025=100). We reference dataflows by id without version, so a bump is transparent to the pull — but every historical value changes. The snapshot model handles it (new vintage, old vintage kept); downstream must use base_period or compute % changes rather than joining raw index levels across vintages. Same class of issue: BA_SA2 is "from July 2021 onwards" — the registry stitches BA_SA2_201116 + BA_SA2_2016-21 + BA_SA2 for 2011→ history; a future ASGS edition will add a fourth.

Series get discontinued or change frequency without notice

Seen today: RPPI ended 2021-Q4, CPI_M ended 2025-09 (absorbed into CPI monthly), LEND_HOUSING is quarterly not monthly. Mitigation: the zero-rows raise, plus an audit warning when a dataset's max period_start is older than 2× its frequency (e.g. a monthly series with nothing for 60 days).

API is labelled "beta"; no SLA, no documented rate limit

It has been stable for years and the same host serves ABS Data Explorer. Keep it to one request per dataset, ≤ 12 requests per run, with the same retry/backoff pattern nswgov uses. The raw snapshot means a parse bug never requires re-hitting the API.

RBA CSV layout is convention, not schema

Header-row count has been stable but the title text is edited occasionally. Keying columns by the Series ID row (not by title) and asserting the expected IDs exist keeps this robust; a missing ID raises with the list of IDs found.

Backwards compatibility

Additive only. No existing partition, manifest, CLI command or sink changes. The Census abs source keeps its name and CLI. Drive sync (scripts/ rclone) picks the new dirs up automatically because it syncs data/ wholesale.

What this does not solve

Postcode-level economics. Every series here is state / capital-city level and joins the property tables on time. Sub-state (SA2/SA4) approvals and population are a follow-up needing an ASGS→postcode correspondence — see D5.
