propertyiq_getdata · branch etl-parquet · downstream: databricks-propertyiq (parquet) + data-qa-agent (csv)

Publish updates-only Parquet to the Databricks lake.

One new command — propertyiq-getdata publish databricks — converts new or changed CSV partitions to Parquet and uploads them to a Unity Catalog volume, where a Databricks Auto Loader pipeline (already shipped in the sibling databricks-propertyiq repo) ingests them exactly-once. Fully backwards compatible: CSV partitions stay canonical and untouched; Parquet publishing runs in parallel as a pure addition. The CSV side is not legacy dead weight — the sibling data-qa-agent project ingests the monolith CSVs (nswgov_df.csv, rentboard_df.csv) via its dlt+dbt pipeline into Postgres marts, so both output formats have a live downstream consumer. This page is the complete, self-contained plan — a fresh Claude session in this repo can execute it top to bottom.

Two problems the plan did not anticipate

caught before it shipped

Bronze would have double-counted everything

Bronze already holds every row ingested from the two monolith CSVs at the volume root. Pointing Auto Loader at landing/ appends the same sales and bonds a second time — every figure in gold would have doubled.

Fixed in resolve_versions: rows whose _source_file does not match the <partition>_<sha8>.parquet contract are dropped. Membership is decided by the filename contract, not a date cutoff, so it stays correct however often the feed is replayed.

real divergence, ~1% of suburbs

initcap disagrees between Postgres and Spark

dbt's Postgres initcap treats any non-alphanumeric as a word boundary, so BRIGHTON-LE-SANDS becomes Brighton-Le-Sands. Spark's F.initcap splits on whitespace only, giving Brighton-le-sands.

50 of 4,583 distinct NSW localities contain a hyphen, comma or ampersand. Sums (n_sold, total_sale_value) are unaffected — only the suburb label, and therefore the mart's row count at suburb grain, differs.

◆ RESOLVED — the NSW Valuer General scraper is fixed; sales now run to 2026-08-10

This section previously reported the sales feed as dead and awaiting a decision. It has since been diagnosed with a real browser and fixed. The page was never JavaScript-rendered — that diagnosis was wrong. Three separate things were going on:

  • A self-referential Referer on the session made the old portal page redirect to itself forever (TooManyRedirects). Isolated header by header; Referer alone reproduces it.
  • The portal endpoint is genuinely retired. It now 302s to a root page that reads "the application you requested is currently unavailable". Other VG services still launch fine, so only this one is gone. The bulk archives moved to valuergeneral.nsw.gov.au/__psi/weekly/YYYYMMDD.zip and /__psi/yearly/YYYY.zip, and that directory index is 403 — there is no listing left to scrape.
  • The 403 on the files themselves is TLS fingerprinting, not JavaScript. A browser fetch pulls the zip; requests is refused whatever headers it sends. curl_cffi impersonating Chrome's handshake returns the byte-identical 345,164-byte file — so the fix is a small library, not a headless browser in the ETL.

Discovery is now enumerate-and-probe: weekly archives are Mondays, so candidates are built locally and confirmed with one HEAD each; a 404 marks the end of published data. 760 partitions, up from 754 — six consecutive weeks recovered with no gaps — and the whole chain re-verified green through gold.

⚑ A bug I introduced fixing it, worth remembering

The first version of the probe used a thread pool with a shared session and a bare except: return False. This host rate-limits concurrency by answering 404 — indistinguishable from "not published yet" — so three weeks that return 200 on every sequential attempt were silently dropped, leaving a real two-week hole in the data that the run still reported as success.

Probing is now sequential by default (a routine run probes about five URLs, so there was nothing to gain by fanning out) and a transport error retries then raises ProbeError rather than quietly shrinking the result. Both behaviours are pinned by tests.

⚠ Two pre-existing problems this surfaced — still unfixed

  • The watermark strands periods. Recovering the last two weeks needed --all-periods, because once the watermark advanced past them the trusted-final filter refused to backfill. A mid-run failure can therefore leave a permanent gap that a normal run will never fill.
  • extract cannot read the yearly archives. --all-periods also pulls them, which crashes with Could not infer YYYYMMDD period for .../ARCHIVE_SALES_2001.DAT. Worked around by scoping extract to the weekly payloads.

Neither is caused by this work, and neither is fixed.

◆ Three divergences found, all explained, none of them money

The harness enforces the additive metrics and reports labelling differences separately, so a real bug can never hide behind a known quirk. All three were tracked to their exact cause:

  • Unparseable postcode — 632 sales (0.025%). dbt's stg_sales has no postcode predicate at all; Databricks silver flags bad_postcode and gold drops the row. Confirmed exactly: 632 rows whose only quality flag is bad_postcode. The check measures this every run rather than assuming it stays small.
  • initcap word boundaries — ~1% of suburb labels. Postgres treats any non-alphanumeric as a word boundary; Spark splits on whitespace only. Same 1,874 suburbs in the sample month, different labels: Brighton-Le-Sands vs Brighton-le-sands, Mount Kuring-Gai vs Mount Kuring-gai, O'Connell vs O'connell, Run-O-Waters vs Run-o-waters.
  • Leading-dot decimals — 1 grain row in 198 months. The lone grain_rows mismatch traced to a Coolongolook parcel recorded as area_sqm=.4, area_type=H. dbt's regex ^[0-9]+(\.[0-9]+)?$ demands a digit before the point, so it drops to NULL and bands as unknown; Spark's numeric regex accepts .4 and bands it correctly as 4,000 m². Spark is the more correct of the two here — this is a latent bug in the dbt model, not in gold.

⚑ Why DuckDB rather than querying data-qa-agent's Postgres

The comparison has to be reproducible without standing up the whole data-qa-agent Docker stack (which was not running). DuckDB's percentile_cont, date_trunc and regex semantics track Postgres closely, so a mismatch means a real logic divergence rather than an engine quirk. The reference deliberately reproduces the Postgres initcap rule, which is how the divergence above surfaced. Partitions are read with pandas — the same reader the publisher uses — because one real partition (period=20151207.csv) carries a malformed quote that DuckDB's CSV sniffer refuses outright.

Why all-STRING when Parquet could carry types?

The repo's own output contract is all-string (dtype=str reads, pinned by tests/test_contract_outputs.py), and the consumer deliberately types in one tested place (its silver layer) because the sales data carries three numeric encodings across its history. Typing at export would silently absorb that mess here, untested. Parquet still buys real NULLs, column pruning and ~4× smaller files.

Why hash-suffixed, append-only names?

Auto Loader tracks files exactly-once and never re-reads a changed file — overwriting in place would silently lose updates. Hash-named new files make rentboard's mutable trailing month just work, and future sales restatements flow through the identical path. One invariant: landing is append-only; the consumer resolves versions.

⚑ Auth: reuse the existing CLI profile, never a token in code

The machine already has an OAuth profile DEFAULT in ~/.databrickscfg (host dbc-f054acc5-b343.cloud.databricks.com). databricks-sdk's WorkspaceClient(profile="DEFAULT") picks it up. Accept --profile (default DEFAULT) and never read, print, or store credentials. Nothing secret may enter this repo — it is public.

07Risks and edge cases

check first

Python 3.14 vs pyarrow wheels

.python-version pins 3.14. If uv add pyarrow cannot resolve a 3.14 wheel, pin the venv to 3.12 (uv python pin 3.12; requires-python >= 3.10 already allows it) and note it in the PR rather than building pyarrow from source.

design guard

Empty-string vs NaN round-trip

Pandas turns "" into NaN by default, which Parquet would store as NULL — silently changing the consumer's strata_no empty-string house/unit rule. keep_default_na=False on the read is load-bearing; the round-trip test pins it.

known, out of scope

Upstream watermark gaps

VG restatements below the watermark never reach the partitions, and a cached partial-month xlsx is never re-fetched (update_rentboard:237). The publish layer faithfully forwards whatever the partitions hold. Optional stretch, only if time allows: re-download the xlsx when it is the watermark month — a two-line change near that cache check — as its own commit.

operational

Interrupted bootstrap

A killed run leaves a valid prefix (uploads are atomic per file, plan is oldest-first, re-run resumes by diff). The one non-obvious case: an upload that failed midway server-side. overwrite=False would then refuse the retry — catch the already-exists error on upload, verify the remote file size matches, and treat a match as success / a mismatch as a hard error naming the file.

⚠ Free Edition quota worth knowing

The volume is backed by managed storage on Free Edition — 868 small Parquet files (~150–250 MB total) is trivial, but do not be tempted to also mirror the raw zips there; that belongs to the (separate, later) lake architecture plan in .lavish/propertyiq_data_architecture_plan.html, which this branch deliberately does not implement. No store_uri abstraction, no fsspec, no Bronze-raw mirroring here — smallest possible diff that satisfies the contract.
