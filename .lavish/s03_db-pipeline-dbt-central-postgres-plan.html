One dbt pipeline that lands every propertyiq dataset in the central database

Today this repo ends at CSV partitions on disk and Google Drive. data-qa-agent re-does its own cleaning of the sales and rent data with a separate dlt + dbt project, and the ABS / RBA economic series reach no database at all. This plan adds a db command to propertyiq_getdata that loads the manifests into a project database propertyiq on the central Postgres and runs a dbt project (raw → staging) there. propertyiq owns landing and clean, typed, record-grain staging for every app to consume; each app owns its own marts. data-qa-agent drops its ingestion (dlt, the CSV/S3 inputs, samples) and keeps only a marts-layer dbt that reads propertyiq staging over postgres_fdw.

What changes — the ownership split

propertyiq_getdata = land + clean. It loads every manifest partition into propertyiq.raw and builds propertyiq.staging: typed, cleaned, record-grain, app-agnostic tables (one row per sale, per bond, per economic observation). That is the layer any app on the platform reads and augments. Apps = marts. data-qa-agent keeps its own marts.* (the postcode × month aggregates, yield, RLS) built by its own dbt — but sourced from propertyiq_staging foreign tables instead of a CSV it ingests itself. Its dlt ingest, the CSV/S3 inputs, the samples and the /data mount are decommissioned; the cleaning rules move here.

02Target architecture

Everything left of the database boundary already exists. The new pieces are the db CLI group (loader + dbt runner), the dbt/ staging project, and the FDW bridge into dataqa. Marts live with the app that needs them.

Solid = exists · green = new in this repo · amber = new in dataqa (one Alembic migration) · dashed strike = decommissioned

Why a separate database, not dataqa.raw

Platform rule D13 is one database per project; the registry, db-init, backups and role grants all assume it. Writing into dataqa would couple this repo's loader to data-qa-agent's Alembic schemas and RLS. postgres_fdw is already installed on the cluster (Postgres 16.14) so the boundary costs one IMPORT FOREIGN SCHEMA.

Why COPY, not dlt

The loader's input is already a clean, typed-by-contract CSV with a sha256 per partition. dlt would add a 40-package dependency, its own _dlt_* state tables and type inference we then have to pin back to text (exactly what data-qa-agent does today). A 60-line psycopg COPY … FROM STDIN per partition is faster and the incremental logic reads straight off the manifest. See §04.

Why staging here, marts there

Cleaning rules belong beside the scraper that knows the quirks (this repo's AGENTS.md already documents the .DAT layout, the bond-board columns, SDMX keys) and they are the same for every consumer. Aggregation grain, thresholds (n_sold ≥ 5), RLS and "which slug may see it" are product decisions — they stay with the app. data-qa-agent's stg_* models and dlt go; its mart_* models and RLS macros stay exactly as they are, re-pointed at foreign tables.

04The loader: propertyiq-getdata db load

A new package propertyiq_getdata/db/, following the repo's split: mechanics in core/-style modules, driven from cli.py. Dependencies land in an optional extra [db] (psycopg[binary], dbt-core, dbt-postgres) so the scrape-only install stays light.

Algorithm (per dataset)

  1. Read the manifest (source, dataset, path, rows, sha256) — it is already the authoritative list of partitions.
  2. Read meta.load_state for that table: (_partition → sha256, rows).
  3. For each manifest row whose sha256 differs or is missing: in one transaction, DELETE … WHERE _partition = $1 (no-op for new snapshots), then COPY raw.t (cols…) FROM STDIN (FORMAT csv, HEADER) streaming the file, then upsert meta.load_state.
  4. Partitions in load_state but no longer in the manifest are deleted (a re-transformed nswgov week that disappears) unless the dataset is snapshot-typed (vintages are never dropped).
  5. Assert loaded row count == manifest rows; mismatch raises, transaction rolls back — same "raise on zero rows" discipline as the sources.
  6. --full-refresh truncates the raw table and forgets its state first; --dataset (append) and --dry-run match the existing CLI conventions.

Table creation & typing

db init creates the four schemas, the two meta tables, and grants (USAGE + SELECT on staging/marts/meta to propertyiq_ro, default privileges so dbt-created tables inherit it). Raw tables are created lazily from the CSV header on first load — every column text, then the three loader columns. A header that differs from the existing table is an error, not an ALTER: the source contract changed and someone should look.

Expected first load on the laptop: ~3.1 M sales rows via COPY ≈ 1–2 min, rent ≈ 1 min, econ series seconds. Weekly incremental: 1 new sales partition, ≤1 rent partition, 0–11 snapshots.

  • Column names and aliases (staging.property_sales, staging.property_rent) — data-qa-agent's mart_*.sql must compile against the foreign tables without edits beyond the source() swap.

  • mart_property_sales/rent/yield.sql, int_/dim_postcode_geo.sql, apply_dataset_rls*, the four mart tests, agent_queryable tags — its marts, its rules.
  • run.py minus the ingest call; dbt build is the whole job. The manifest it generates still feeds DBT_MANIFEST; propertyiq's staging descriptions reach the agent through that project's _sources.yml.

New tests worth having

  • econ_series: unique (series_id, period_start); every seed series_id exists in staging (catches an ABS key change).
  • econ_headline_series ⋈ econ_series: every curated series has an observation in the last 2 quarters (catches an ABS key change or a broken dataflow).
  • Source freshness: raw.nswgov_sales._loaded_at warn > 10 d, error > 21 d.
  • staging.property_*: row-count parity per year with data-qa-agent's last staging.property_* build (one-off, during cut-over).
