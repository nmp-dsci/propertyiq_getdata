PropertyIQ should become a lake-first ingestion system

Keep source data and normalized analytical datasets in a portable object-store lake. Treat the database as a serving projection for the app and AI agent, not as the canonical data store.

Recommendation

Move from repo-local CSV folders plus Google Drive sync to a portable data lake layout: raw source files in Bronze, normalized Parquet in Silver, database-ready views or exports in Gold/Serving.

Boundary

This repo should own extract, raw preservation, normalization, manifests, and publishable datasets. The database project should load and serve app-specific models unless you explicitly change the repo contract.

Why not DB-first?

Raw files, historical snapshots, and wide ABS data are better preserved in object storage. Databases are ideal for low-latency serving, constraints, joins, and AI-agent retrieval paths.

Proposed Lake Layout

Canonical object-store prefixes

propertyiq-lake/ bronze/ raw/nswgov/sales/period=YYYYMMDD/run_id=.../original.zip raw/rentboard/lodgements/year=YYYY/month=MM/run_id=.../original.xlsx raw/abs/gcp/geography=POA/state=NSW/census_year=YYYY/run_id=.../original.zip metadata/source_fetch_log/year=YYYY/month=MM/*.jsonl stage/ nswgov/output_etl2/period=YYYYMMDD/*.parquet abs/table_extracts/census_year=YYYY/state=NSW/geography=POA/table=G01/*.parquet silver/ nswgov/sales/period=YYYYMMDD/*.parquet rentboard/lodgements/year=YYYY/month=MM/*.parquet abs/poa/census_year=YYYY/*.parquet abs/poa_columns/census_year=YYYY/*.parquet registry/ datasets/*.yaml manifests/source=.../dataset=.../*.parquet runs/year=YYYY/month=MM/*.jsonl exports/ csv/normalized/... # compatibility only

Layer meanings

  • Bronze Raw, source-fidelity files. Do not rewrite. Store original format and metadata.
  • Stage Rebuildable extracts. Keep short retention locally or in cloud only when debugging value is high.
  • Silver Normalized, source-specific analytical datasets. This is the main output of this repo.
  • Gold/Serving App-ready joins/features/search tables. Prefer the downstream database project for this layer.
Use PROPERTYIQ_STORE_URI=file:///... for local development and s3://, gs://, or Azure Blob in production.
For a local-only setup, keep scratch files in this repo's git-ignored data/ folder, but put the durable lake somewhere outside the repo, such as ~/propertyiq-lake or an external disk. Point PROPERTYIQ_STORE_URI at that folder.

Phase 0: Decide ownership and vocabulary

Update README/AGENTS only if the boundary changes. The current repo instructions say database loading belongs elsewhere; the cleaner architecture keeps it that way.

  • Rename local concept from data_dir to work_dir for scratch/cache.
  • Add store_uri for canonical data lake root.
  • Define dataset IDs: nswgov.sales, rentboard.lodgements, abs.poa, abs.poa_columns.

Phase 1: Add portable storage without rewriting sources

Keep local extraction because ZIP and pandas workflows expect files. Publish raw and final artifacts to the storage backend after each stage.

  • Add propertyiq_getdata/core/storage.py wrapping fsspec/pyarrow.
  • Add --store-uri and PROPERTYIQ_STORE_URI; preserve --data-dir as local compatibility.
  • Replace rclone Drive scripts with backend-agnostic publish and pull-cache commands.

Phase 2: Make Parquet canonical

Write normalized CSV and Parquet for one release, then flip Parquet to canonical and keep CSV under exports/csv.

  • Add atomic_write_parquet using local temp then backend put/copy.
  • Use Hive-style partitions matching current contract: period=YYYYMMDD, year=YYYY/month=MM, census_year=YYYY.
  • Pin schemas in tests and write a companion schema registry YAML/JSON per dataset.

Phase 3: Run serverlessly

Package the CLI in a container. The same command runs locally, in GitHub Actions, or in cloud jobs.

  • Simple path: GitHub Actions schedule for weekly NSW/rentboard updates, manual ABS workflow.
  • Robust path: Prefect push work pool, Cloud Run Job, AWS ECS/Fargate task, or Azure Container Instance.
  • AWS-specific path: EventBridge + Step Functions + container tasks; query with Athena over S3.

Phase 4: Formalize the database loader contract

The database project should load from the lake manifest, not from ad hoc local paths. That gives repeatability and lets the app/AI serving layer be rebuilt from a known lake snapshot.

Input

Dataset manifest rows with path, sha256, rows, schema version, period, object generation/version.

Load method

Stage table, validate counts/checksums, upsert or replace affected period, record load_runs.

Serving

Postgres/app DB for low-latency reads, joined entities, search indexes, embeddings, and agent tools.

Risks And Controls

Risk Control
Partial writes to object storage are not the same as POSIX atomic replace. Write to run-scoped temporary keys, validate checksum/row counts, then publish a manifest pointer as the commit record. Use Iceberg later if transactional table commits become necessary.
CSV-to-Parquet migration can break downstream loaders. Dual-write for one release; keep CSV export command; version schemas and update database project loader to read manifests.
ABS wide output can stress memory and file size. Use pyarrow/DuckDB for conversion; keep one census-year partition but consider row-group sizing and compression. Do not force the wide ABS table into the app database unless needed.
Cloud choice can lock in orchestration and query engine. Use object-store URI abstraction and open formats first. Keep provider-specific services at the edges.
Raw data retention can grow indefinitely. Lifecycle policies: retain Bronze indefinitely or archive after one year; expire Stage after 30-90 days; keep Silver and manifests as canonical historical record.

Decisions To Make Before Coding

Cloud target

If you already have a preferred cloud, use its object store. If not, start with local filesystem plus S3-compatible MinIO for dev and S3 for production.

Canonical table format

Start with Parquet + manifests. Add Iceberg when you need SQL table commits, schema evolution, time travel, or multi-engine concurrency.

Repository boundary

Either keep DB loading in the database project, or explicitly change this repo's charter. The current repo contract says collection only.

AI-agent serving

Use the serving DB/vector index for low-latency agent tools. Use the lake for provenance, backfills, analytics, and rebuilds.

Research Basis

AWS recommended data lake layers: raw, stage, analytics; keep original raw format and enable versioning Apache Parquet: column-oriented format for efficient storage and retrieval fsspec: generic filesystem API over local and remote storage PyArrow filesystems: native S3 and GCS support DuckDB: Hive partitioned Parquet datasets Apache Iceberg spec: metadata files, snapshots, optimistic concurrency Amazon Athena: querying Iceberg tables on S3 Delta Lake: ACID transactions and scalable metadata on data lakes BigQuery: loading Parquet from Cloud Storage Azure Synapse serverless SQL: query Parquet/Delta/CSV in data lake lakeFS: Git-like versioning over object storage, optional later Prefect push work pools: serverless flow runs without a worker
